## Restored contract

The old ConverterLuaObject turns ILuaObject into a table whose value field contains an OC Value implementing ManagedPeripheral. Modern CC replaced ILuaObject with IDynamicLuaObject and also exposes annotated @LuaFunction objects. The optional registration previously installed only peripheral/media drivers, so foreign objects fell back to their Java toString text.

LuaObjectConverter is registered only when CC is installed. It uses the pinned CC LuaMethodSupplier for dynamic methods, annotations, aliases and main-thread annotations, and reuses ComputerCraftArguments for UTF-8, raw bytes, ByteBuffer and nested table conversion. The legacy value-field wrapper remains. The serialized ComputerCraftLuaObjectValue shell has no CC type references; its public no-argument constructor exposes no methods and direct Java invoke returns nil plus ComputerCraft userdata cannot be persisted. Its foreign delegate is transient and load/dispose cancels owned work.

Calls defer off the server thread with LimitReachedException before side effects. executeMainThreadTask executes once on the server thread. issueMainThreadTask schedules owned work for a later server tick and sends task_complete with ID/success/results or an error to the invoking OC Context. Object and peripheral tasks share the existing task-ID allocator, preventing same-computer collisions. Dispose and server stop cancel pending object work; weak handle tracking does not retain otherwise unreachable live objects. Own task-completion callbacks can be resolved during a call, bounded at64 resumptions; arbitrary external-event waits/yields are explicitly unsupported, consistent with the old unsupported Lua context and existing peripheral bridge. This does not create a second Lua coroutine/event runtime.

The Java and Lua error layers differ. CC LuaException is an OC soft error, observed from Lua as nil, reason. After restore the existing kernel rechecks a userdata callback's current method set. An expired shell exposes no methods, so a retained Lua callback raises no such method; the shell's direct Java invoke still returns the legacy explanatory persistence error. No kernel error policy or fake live context was added.
